# Архитектура

## Сборка контейнеров

Node LTS и Caddy закреплены version tags и digest. В Node-слое установлена исправленная системная `zlib1g`. Caddy 2.11.9 собирается официальным `xcaddy` с `golang.org/x/net` 0.62.0: официальный runtime-образ пока содержит уязвимую версию этого модуля. Build toolchain в итоговый frontend-образ не переносится. При обновлении базовых образов эти точечные исправления следует перепроверить по image scan.

## Runtime-границы

Production состоит из двух неизменяемых контейнеров. Caddy отдаёт PWA и проксирует `/api/*` во внутренний Fastify API. Внешний Nginx завершает TLS и перенаправляет запросы на `127.0.0.1:18080`. API не публикует host port и единолично получает credentials Mistral и Deepgram.

React отображает setup и live-экраны. Dexie владеет долговременными настройками и Blob-ссылками, Zustand содержит только состояние активной сессии. `SessionManager` создаёт и останавливает media, viewer, like, reaction, comment, AI и speech pipeline. Все пути остановки сходятся к идемпотентному освобождению MediaStream, AudioContext, AudioWorklet, WebSocket, object URL, listeners и timers.

Публичной пользовательской аутентификации нет. Origin validation, ограничения тела запроса, rate limit и idempotency защищают границу API, но не заменяют upstream access control.

## Речь

AudioWorklet преобразует микрофон в mono Linear16 и отправляет бинарные фрагменты через same-origin WebSocket. Fastify держит одно соединение с Deepgram Flux. Только завершённые нормализованные реплики попадают в ограниченное окно transcript и запускают анализ контекста.

В контракте нет уровня сигнала, clipping, packet loss, confidence слышимости или состояния микрофона. Transcript является только текстом. Mistral запрещено создавать или сохранять выводы о слышимости и качестве звука; domain validation отклоняет такие выводы на уровне semantic context и комментариев. Обычное обсуждение музыки или выбора микрофона разрешено.

Сбой speech stream восстанавливается с ограниченным exponential backoff и не останавливает видео или остальные движки. API не сохраняет и не логирует аудио и transcript.

## Контекст и зрение

Frame pipeline создаёт ограниченный JPEG при значимом изменении сцены или принудительном обновлении. Визуальный вопрос ведущего запрашивает свежий кадр; устаревший кадр не может подтвердить предмет.

Context model получает новый transcript suffix, ограниченную историю и текущий кадр. Она возвращает JSON Schema с темой, намерением ведущего, точным адресатом, presenter context, audience direction и `visualGrounding`. JSON проходит Zod и предметную валидацию. Один невалидный ответ получает один repair-запрос.

`visualGrounding` имеет состояния `none`, `uncertain`, `confirmed`. Первый кадр допускает только `uncertain`; `confirmed` требует совпадающего независимого наблюдения на следующем свежем кадре. Противоречие, отсутствие различающего признака или смена темы очищают claim. `sceneSummary` описывает только общую композицию и не является источником названий предметов.

Presenter context содержит настроенного ведущего и не более двух временных гостей. Допустимы только нейтральные visual anchors. Система не создаёт биометрический шаблон, не распознаёт личность и не угадывает возраст, пол, отношения или другие чувствительные признаки. Имя гостя принимается только из новой речи.

## Комментарии и диалоги

Локальный director выбирает автора, язык, назначение, длину, casing, разрешение emoji/опечатки, точную reply-связь и право визуального утверждения. Comment model пишет только текст для подготовленных слотов и не управляет авторами или расписанием.

Явное приглашение задавать вопросы является одноразовым intent. Оно занимает первые два или три слота конкретными вопросами; presenter events, viewer-to-viewer ветки и старые host-диалоги не могут их вытеснить. Пачка не считается выполненной, пока после единственного repair не приняты все запланированные question slots. Следующая пачка без новой просьбы возвращается к обычному распределению.

Host/viewer dialogue хранит до трёх веток, шести ходов и 120 секунд. Вопрос открывает ветку только после появления на экране. Ответ ведущего продолжает ветку при точном username/display name или однозначном semantic target; близость по времени не является адресацией. Каждая реплика ссылается на конкретный `turnId`.

Viewer-to-viewer диалоги редкие и причинно упорядочены: reply становится доступен только после показа target и дополнительной задержки. Очередь, novelty history, persona memory, transcript и DOM имеют жёсткие лимиты.

Topic reset увеличивает `topicResetSequence` и атомарно очищает старые диалоги, очередь, novelty, persona memory и recent-comment context. Ответ из предыдущей эпохи не принимается.

Сгенерированная пачка проверяется на schema, slot/persona, язык, длину, emoji, копирование transcript/identity, дубликаты, визуальные и аудио-утверждения. Repair получает только отсутствующие слоты и уже принятые тексты. Если usable result отсутствует или invitation потерял обязательный вопрос, API возвращает retryable `AI_RESPONSE_INVALID`; backoff затрагивает только комментарии.

## PWA и данные

Service worker precache содержит только app shell. Хешированные assets имеют immutable cache, а HTML, manifest и service worker не имеют. Пользовательские media, IndexedDB и provider payloads не попадают в HTTP cache.

Кадры, аудио, transcript, semantic context, persona runtime и комментарии существуют только во время обработки. API их не сохраняет. Подробные лимиты и durable schema описаны в [DATA_MODEL.md](DATA_MODEL.md).
